# TripMate AI Agent 설계서

---

## 1. 개요·목적

### 해결하려는 문제

바쁜 직장인은 주말여행을 계획할 때 숙소·교통·맛집·날씨·동선을 각각 따로 검색해야 해서 계획 자체에 수 시간이 걸린다. TripMate는 목적지·날짜·예산·인원만 입력하면 숙소 비교부터 하루 단위 동선까지 여행 계획 전체를 자동으로 완성해준다.

### 타깃 사용자

주말 여행을 원하지만 계획 세울 시간이 부족한 20~40대 직장인.

### 왜 Agent여야 하는가

단일 LLM 호출은 실시간 숙소 가격·잔여 객실·현재 날씨 같은 외부 데이터를 가져올 수 없어서 실제로 쓸 수 있는 계획이 나오지 않는다. RAG는 정적인 문서를 검색하는 구조라 "지금 이 날짜에 이 가격으로 예약 가능한 숙소"처럼 동적으로 변하는 정보를 다루기 어렵다. Workflow는 실행 순서가 고정돼 있어서, 예를 들어 "당일치기 강릉 맛집 위주"처럼 숙소 검색이 필요 없는 요청과 "2박3일 제주 숙소 먼저 잡고 동선 짜기"처럼 숙소가 기준이 되는 요청을 같은 흐름으로 처리할 수 없다.

TripMate는 사용자 요청에 따라 어떤 Tool을 어떤 순서로 호출할지를 매번 다르게 결정해야 한다. "혼자 당일치기 전주 한옥마을"이면 장소 검색 → 교통 조회 → 날씨 확인 순으로 동작하고, "커플 2박3일 부산 예산 30만원"이면 숙소 검색 → 예산 배분 → 맛집·장소 검색 → 동선 최적화 순으로 동작한다. 이처럼 실행 경로 자체가 요청마다 달라지기 때문에 Agent 구조가 필요하다.

## 2. 사용자 시나리오

### Persona

- **이름:** 김장훈 (32세)
- **역할:** 서울 직장인, 마케팅팀 대리
- **목적:** 주말에 짧게라도 여행을 다니고 싶지만 퇴근 후 계획 세울 여력이 없음. 금요일 저녁에 "이번 주말 어디 갈까" 고민하다가 결국 집에 있는 패턴이 반복되고 있음.

---

### 요청 1 — 당일치기, 목적지 미정

> "이번 주 일요일에 혼자 당일치기 하고 싶어. 서울에서 2시간 이내, 자연 보고 싶고 예산은 5만원 이하."

**단일 Tool로 안 되는 이유:** 목적지 후보 검색 → 각 후보별 교통 소요시간 조회 → 날씨 확인 → 장소 추천 → 동선 구성까지 순차적으로 여러 Tool이 필요하고, 날씨나 교통 결과에 따라 후보지가 바뀔 수 있음.

### 요청 2 — 2박3일, 숙소가 핵심

> "다음 주 금토일로 부산 2박3일 가려고. 친구랑 둘이서 숙소 예산 1인 3만원 이하로 맞춰줄 수 있어? 해운대 근처였으면 좋겠어."

**단일 Tool로 안 되는 이유:** 숙소 검색·비교가 먼저고, 숙소 위치 확정 후 주변 맛집·관광지 검색, 날씨 확인, 하루 단위 동선 구성까지 Tool 조합이 요청 1과 완전히 달라짐.

### 요청 3 — 테마 중심, 일정 유동적

> "제주도 카페 투어 하고 싶어. 1박2일인데 유명한 카페 위주로 동선 짜주고, 숙소는 감성 있는 데로 추천해줘. 예산은 넉넉하게 잡을게."

**단일 Tool로 안 되는 이유:** 테마(카페) 기반으로 장소를 먼저 모아서 동선을 짠 뒤 숙소를 동선 중간지점 근처에서 검색하는 순서라, 요청 1·2와 Tool 호출 순서 자체가 다름. 예산 제약이 없어서 예산 계산 Tool은 생략됨.

## 3. 기능 요구사항

### Must-have

1. **숙소 검색 및 비교**
   목적지·날짜·인원·예산을 입력받아, 조건에 맞는 숙소 후보 3개 이상을 가격·위치·평점과 함께 출력한다.

2. **장소·맛집 추천 및 동선 구성**
   목적지·테마·인원을 입력받아, 추천 장소 목록과 하루 단위 방문 순서(오전→오후→저녁)를 출력한다.

3. **교통 정보 조회**
   출발지·목적지·날짜를 입력받아, 이동 수단별 소요시간과 대략적 비용을 출력한다.

4. **날씨 확인**
   목적지·날짜를 입력받아, 여행 기간의 날씨 예보와 우천 시 대안 일정 여부를 출력한다.

5. **예산 배분 계산**
   총 예산·인원·여행 일수를 입력받아, 숙소·식비·교통·여가 항목별 권장 예산을 출력한다.

### Nice-to-have

1. **실시간 혼잡도 반영**
   장소명·날짜·시간대를 입력받아, 예상 혼잡도를 바탕으로 방문 순서 조정 제안을 출력한다.

2. **대안 일정 자동 생성**
   날씨 불량 또는 숙소 만실 시, 동일 조건에서 대체 목적지나 대체 숙소 후보를 자동으로 출력한다.

3. **여행 요약 정리본 출력**
   완성된 일정을 날짜별 표 형태(장소·시간·비용 포함)로 정리해서 저장 가능한 형태로 출력한다.

## 4. Agent 패턴 선택과 근거

### 선택한 패턴: ReAct 기반 + Reflection 부분 적용

### 선택 근거

ReAct를 메인으로 쓰는 이유는 요청마다 스텝 수와 Tool 조합이 달라지기 때문이다. "당일치기"는 3~4스텝, "2박3일 숙소+동선"은 7~8스텝으로 매번 달라져서 Plan-and-Execute처럼 미리 전체 계획을 고정하면 중간에 날씨나 숙소 만실 같은 변수를 처리하기 어렵다. Reflection은 최종 일정 초안이 나왔을 때 "예산 초과 여부", "동선 비효율 여부"를 자체 검토하는 용도로 한 번만 적용한다.

### 루프 구조

```
[사용자 입력]
  "부산 2박3일 친구랑 숙소 1인 3만원 이하"

LOOP:
  Thought: 요청 분석 → 숙소 조건 먼저 확인 필요
  Action:  숙소_검색 Tool 호출
  Observation: 숙소 후보 3개 반환

  Thought: 숙소 위치 확정 → 날씨 확인 필요
  Action:  날씨_조회 Tool 호출
  Observation: 날씨 예보 반환

  Thought: 야외 일정 가능 → 장소 검색 필요
  Action:  장소_검색 Tool 호출
  Observation: 장소 목록 반환

  Thought: 예산 배분 필요
  Action:  예산_계산 Tool 호출
  Observation: 항목별 권장 예산 반환

  Thought: 교통 정보 필요
  Action:  교통_조회 Tool 호출
  Observation: 수단별 소요시간·비용 반환

  Thought: 동선 구성 가능 → 일정 초안 작성
  [Reflection: 예산 초과 없는지, 동선 비효율 없는지 자체 검토]
  → 문제 없으면 최종 출력
  → 문제 있으면 해당 스텝으로 돌아가 재조회

[최종 출력: 날짜별 일정표]

종료 조건: 최종 일정 완성 or max 10 steps 도달
```

### 정상 흐름 — 요청 2 기준 (부산 2박3일, 2인, 숙소 1인 3만원 이하)

```
Step 1.
Thought: 목적지는 부산, 2박3일, 2인, 숙소 예산 1인 3만원 이하.
         숙소가 핵심 제약이므로 숙소 검색을 먼저 해야 한다.
Action:  숙소_검색(destination="부산 해운대", check_in="2025-05-09",
                   check_out="2025-05-11", people=2, max_price_per_person=30000)
Observation: 후보 3개 반환
             - 게스트하우스A: 25,000원/인, 해운대 도보 5분, 평점 4.3
             - 호텔B: 29,000원/인, 해운대 도보 10분, 평점 4.1
             - 펜션C: 28,000원/인, 광안리, 평점 4.5

Step 2.
Thought: 숙소 후보가 해운대·광안리에 분포함.
         날씨 먼저 확인해서 야외/실내 일정 방향 결정 필요.
Action:  날씨_조회(destination="부산",
                   dates=["2025-05-09","2025-05-10","2025-05-11"])
Observation: 09일 맑음, 10일 맑음, 11일 오전 흐림/오후 맑음

Step 3.
Thought: 날씨 양호. 야외 일정 중심으로 구성 가능.
         해운대 근처 장소·맛집 검색 시작.
Action:  장소_검색(destination="부산", theme="맛집+해변+야경",
                   days=3, base_location="해운대")
Observation: 장소 12개 반환
             (해운대 해수욕장, 광안대교 야경, 깡통시장, 국제시장,
              용두산공원, 맛집 6개 포함)

Step 4.
Thought: 장소 목록 확보. 예산 배분 계산 필요.
Action:  예산_계산(total_budget=null, people=2, days=3,
                   accommodation_cost=100000)
Observation: 숙소 100,000원 (25,000원 × 2인 × 2박)
             식비 권장: 60,000원 (1인 1만원/끼니 기준)
             교통 권장: 40,000원 (고속버스 왕복 기준)
             여가 권장: 20,000원
             총 예상: 220,000원/인

Step 5.
Thought: 교통 정보 조회 필요. 서울 → 부산 기준.
Action:  교통_조회(origin="서울", destination="부산",
                   date="2025-05-09", return_date="2025-05-11")
Observation: KTX 2시간 50분, 편도 59,800원
             고속버스 4시간 10분, 편도 23,900원

Step 6.
Thought: 장소·숙소·날씨·예산·교통 정보 모두 확보.
         하루 단위 동선 구성 후 Reflection 진행.
[일정 초안]
  09일(금): 서울 출발 → 게스트하우스A 체크인 → 해운대 해수욕장 → 저녁 돼지국밥
  10일(토): 아침 씨앗호떡 → 광안리 → 국제시장 → 광안대교 야경
  11일(일): 오전 용두산공원 → 깡통시장 점심 → 서울 귀환

[Reflection]
  - 예산 초과 여부: 총 220,000원/인 → 이상 없음
  - 동선 비효율 여부: 해운대↔광안리 반복 이동 없음 → 이상 없음
  - 날씨 위험: 11일 오전 흐림 → 실내(용두산공원 케이블카) 배치 → 적절

Action: 최종 일정 출력
```

### 예외 흐름

| 상황               | Agent 동작                                                              |
| ------------------ | ----------------------------------------------------------------------- |
| 숙소 검색 결과 0건 | 예산 조건 완화 후 재검색. 재검색도 0건이면 인근 지역 대안 제시          |
| 날씨 조회 API 실패 | `{error: "날씨 조회 실패"}` 반환 → 날씨 정보 없이 진행, warnings에 명시 |
| 목적지 미입력      | 테마·날짜·예산 기반으로 목적지 후보 3개 제안 후 사용자 선택 대기        |
| max steps 도달     | 현재까지 확보된 정보로 부분 일정 출력, 미완성 항목 warnings에 명시      |
| 예산 초과 감지     | Reflection 단계에서 감지 → 숙소 등급 하향 또는 교통 수단 변경 후 재계산 |

### 종료 조건

- 최종 일정 출력 완료 시 정상 종료
- max steps: 10 스텝 초과 시 강제 종료 후 부분 결과 출력
- 반복 탐지: 동일 Tool을 동일 파라미터로 3회 이상 호출 시 중단 후 사용자에게 재입력 요청

## 6. Tool 명세

### Tool 1: 숙소\_검색

| 항목         | 내용                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| 목적         | 목적지·날짜·인원·예산 조건에 맞는 숙소 후보를 검색하고 비교 정보를 반환                                            |
| 사용 조건    | 숙소가 필요한 여행(1박 이상)이고, 목적지와 날짜가 확정된 경우                                                      |
| 입력         | `destination: string`, `check_in: string`, `check_out: string`, `people: int`, `max_price_per_person: int \| null` |
| 출력         | `[{name, price_per_night, location, rating, distance_to_center}]`                                                  |
| 실패 시 반환 | `{error: "숙소 검색 실패", detail: "조건에 맞는 숙소 없음 또는 API 오류"}`                                         |

### Tool 2: 장소\_검색

| 항목         | 내용                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------- |
| 목적         | 목적지와 테마를 기반으로 관광지·맛집·카페 등 방문 장소 목록을 반환                           |
| 사용 조건    | 목적지가 확정된 후, 어떤 장소를 방문할지 탐색이 필요한 경우                                  |
| 입력         | `destination: string`, `theme: string \| null`, `days: int`, `base_location: string \| null` |
| 출력         | `[{name, category, location, rating, opening_hours, tip}]`                                   |
| 실패 시 반환 | `{error: "장소 검색 실패", detail: "검색 결과 없음 또는 API 오류"}`                          |

### Tool 3: 날씨\_조회

| 항목         | 내용                                                                       |
| ------------ | -------------------------------------------------------------------------- |
| 목적         | 여행 날짜의 목적지 날씨 예보를 반환해 야외/실내 일정 구성 판단에 활용      |
| 사용 조건    | 목적지와 여행 날짜가 확정된 후 일정 구성 전에 항상 호출                    |
| 입력         | `destination: string`, `dates: [string]`                                   |
| 출력         | `[{date, condition, temperature_high, temperature_low, rain_probability}]` |
| 실패 시 반환 | `{error: "날씨 조회 실패", detail: "API 오류 또는 예보 불가 날짜"}`        |

### Tool 4: 교통\_조회

| 항목         | 내용                                                                                   |
| ------------ | -------------------------------------------------------------------------------------- |
| 목적         | 출발지에서 목적지까지 이동 수단별 소요시간과 비용을 반환                               |
| 사용 조건    | 목적지가 확정된 후, 교통편 정보가 필요한 경우                                          |
| 입력         | `origin: string`, `destination: string`, `date: string`, `return_date: string \| null` |
| 출력         | `[{mode, duration_minutes, cost_one_way, cost_round_trip, memo}]`                      |
| 실패 시 반환 | `{error: "교통 조회 실패", detail: "노선 없음 또는 API 오류"}`                         |

### Tool 5: 예산\_계산

| 항목         | 내용                                                                               |
| ------------ | ---------------------------------------------------------------------------------- |
| 목적         | 총 예산·인원·일수·숙소 비용을 입력받아 항목별 권장 예산을 배분해서 반환            |
| 사용 조건    | 숙소 비용이 확정된 후, 남은 예산을 식비·교통·여가로 나눠야 할 때                   |
| 입력         | `total_budget: int \| null`, `people: int`, `days: int`, `accommodation_cost: int` |
| 출력         | `{accommodation, food, transport, activity, total}`                                |
| 실패 시 반환 | `{error: "예산 계산 실패", detail: "입력값 오류"}`                                 |

### Tool 호출 순서 요약

```
숙소 필요 여행:  숙소_검색 → 날씨_조회 → 장소_검색 → 예산_계산 → 교통_조회
당일치기:        날씨_조회 → 장소_검색 → 교통_조회 → 예산_계산  (숙소_검색 생략)
테마 중심:       장소_검색 → 숙소_검색 → 날씨_조회 → 예산_계산  (순서 다름)
```

## 8. 성공 판정 기준

| #   | 판정 항목                   | 판정 방법            | 기대값             |
| --- | --------------------------- | -------------------- | ------------------ |
| 1   | 숙소 필요 시 Tool 호출 순서 | trajectory 로그      | 숙소\_검색 먼저    |
| 2   | 당일치기 시 숙소 Tool 생략  | trajectory 로그      | 미호출             |
| 3   | Tool 실패 시 fallback       | error 후 Action 확인 | 재검색 또는 대안   |
| 4   | 최종 출력 필수 필드         | 출력 JSON 필드 확인  | 4개 필드 모두 존재 |
| 5   | 스텝 수 이내 종료           | 스텝 수 카운트       | 10 이하            |
| 6   | Reflection 예산 재조정      | Reflection 후 Action | 재조정 시도        |

**체크리스트 상세:**

1. **Tool 호출 순서** — 숙소가 필요한 요청(1박 이상)에 대해 `숙소_검색` Tool이 `장소_검색` Tool보다 먼저 호출되는가?

2. **당일치기 시 숙소 Tool 생략** — 당일치기 요청에 대해 `숙소_검색` Tool을 호출하지 않는가?

3. **Tool 실패 시 fallback 동작** — `숙소_검색` Tool이 결과 0건을 반환했을 때, 예산 조건을 완화하거나 인근 지역으로 대체 검색을 시도하는가?

4. **최종 출력 필수 필드 포함** — 최종 응답에 `schedule`, `accommodation`, `budget_breakdown`, `transport` 4개 필드가 모두 포함되는가?

5. **스텝 수 및 종료 조건** — 정상 요청에 대해 10 스텝 이내에 최종 일정을 출력하고 종료하는가?

6. **Reflection 예산 검증** — Reflection 단계에서 예산 초과가 감지됐을 때, 숙소 등급 하향 또는 교통 수단 변경을 통해 예산 내 재조정을 시도하는가?

## 9. 제약·확장

### 현재 설계의 한계

1. **실시간 예약 불가** — 숙소·교통 Tool이 검색과 비교까지만 하고 실제 예약으로 이어지지 않는다. 사용자가 결과를 보고 직접 예약 사이트로 이동해야 한다.

2. **사용자 취향 누적 불가** — 현재 설계는 대화 1회가 끝나면 상태가 초기화된다. "저번에 부산 갔을 때 좋았던 숙소 스타일로 이번에도 추천해줘" 같은 요청을 처리할 수 없다.

3. **동행자 선호 조율 불가** — "친구랑 둘이 가는데 친구는 맛집 위주, 나는 자연 위주"처럼 동행자 간 선호가 다를 때 단일 Agent가 조율하기 어렵다.

4. **예약 가능 여부 실시간 검증 불가** — 숙소·교통 Tool이 Mock 기반이라 실제 잔여석·잔여 객실을 보장하지 못한다. 추천한 숙소가 실제로는 만실일 수 있다.

5. **장거리 이동 중간 경유지 최적화 미지원** — 서울 → 제주처럼 항공이 필요한 경우나 경유지가 있는 복잡한 동선은 현재 교통\_조회 Tool로 처리하기 어렵다.

### Multi-Agent 확장 시 역할 분리 후보

현재는 단일 Agent가 숙소·장소·날씨·교통·예산을 모두 담당하는데, 요청이 복잡해질수록 LLM이 Tool을 고르다가 실수할 가능성이 높아진다. 아래처럼 쪼갤 수 있다.

```
[Orchestrator Agent]
  사용자 요청 분석 → 하위 Agent에 작업 분배 → 결과 취합 → 최종 출력

  ├── [숙소 Agent]
  │     숙소 검색·비교·대안 제시 전담
  │     Tool: 숙소_검색
  │
  ├── [일정 Agent]
  │     장소 검색·동선 구성·날씨 반영 전담
  │     Tool: 장소_검색, 날씨_조회
  │
  ├── [교통 Agent]
  │     출발지→목적지 교통편 탐색 전담
  │     Tool: 교통_조회
  │
  └── [예산 Agent]
        전체 비용 취합·항목별 배분·초과 감지 전담
        Tool: 예산_계산
```

이렇게 쪼개면 각 Agent가 담당 Tool만 집중해서 쓰기 때문에 Tool 선택 오류가 줄고, Orchestrator가 숙소·일정·교통을 병렬로 동시에 조회할 수 있어서 응답 속도도 빨라진다.

### 장기 상태·메모리가 필요해지는 시나리오

1. **여행 이력 기반 추천** — "저번 강릉 여행에서 묵었던 숙소 스타일로 이번에도 찾아줘" → 과거 여행 기록을 저장하고 참조하는 메모리 필요.

2. **사용자 취향 프로파일 누적** — "나는 항상 조용한 숙소 선호, 맛집보다 자연 위주" → 대화가 쌓일수록 취향 벡터를 업데이트하는 장기 메모리 필요.

3. **예산 관리 연속성** — "이번 달 여행 예산 총 50만원인데 저번 주 제주에서 20만원 썼어, 이번 주 강릉은 얼마까지 써도 돼?" → 월별 예산 상태를 유지하는 상태 메모리 필요.
