## 1. Golden Dataset

### 1) 정의

AI 성능 지표를 테스트하기 위한 데이터셋을 의미합니다.

### 2) 필요한 이유

- 실제 일어날 수 있는 다양한 시나리오, 통계적으로 결론을 내릴 수 있을 만한 데이터를 통해 실제 테스트를 해야 AI 의 신뢰도를 측정할 수 있기 때문입니다.

### 3) 필수 스키마 (v0.2+)

| 필드 | 설명 |
|---|---|
| `user_input` | 사용자가 시스템에 던지는 질문이나 프롬프트 |
| `reference` | 평가의 기준이 되는 실제 정답 또는 모범 답안 |
| `retrieved_contexts` | AI 가 답변을 생성하기 위해 데이터베이스(Vector DB 등)에서 검색해 온 참고 문서 |
| `reference` | 평가의 기준이 되는 실제 정답 또는 모범 답안 |

### 4) 권장 규모

| 단계 | 권장 개수 | 근거 |
| --- | --- | --- |
| 초기 (PoC) | 20 ~ 50개 | 핵심 기능 검증 및 주요 실패 케이스 식별을 위한 최소 갯수입니다. |
| 성숙 (Prod) | 100 ~ 300개 | 다양한 시나리오들이 생기기에 각 케이스별 데이터셋 추가 |
| 대규모 (Scale) | 500개 이상 | 새로운 기능이 추가되거나 수정되면, 회귀 테스트가 필요하기에 대규모 데이터셋을 필요로 합니다. |

### 5) 양보다 질 — 좋은 Dataset 조건

- 품질이 높은 데이터 샘플을 가지고 있어야 합니다.
- 여러 가지 시나리오를 가지고 있어야 합니다.
- 지속적으로 데이터를 업데이트시켜줘야 합니다.

### 6) `ground_truth_contexts` 수동 어노테이션 이유 (어느 메트릭에 필수인지)

> **정답이 어디에 있는지** 를 사람이 지정한 데이터입니다.

- 실제로 정답을 포함하고 있는 문서가 무엇인지 정의해둬야 모델이 검색을 제대로 했는지 객관적 평가를 할 수 있습니다.
- 이를 통해 환각을 검증할 수 있습니다.

**필수 메트릭**

- **Context Precision** — 검색된 문서들이 정답을 포함하고 있는지 확인하기 위해 필요
- **Context Recall** — 필요 정보를 포함하고 있는가를 확인하기 위해 필요
- **Faithfulness** — 정답지를 비교해서 충실히 대답했는가를 확인하기 위해 필요

## 2. 평가의 필요성과 LLM-as-a-Judge

### 2-1. 왜 체계적 평가가 필요한가

AI Agent 나 RAG 파이프라인 구축 시, 해당 AI 가 정말로 잘 작동하고 있는지 정확힐 알 수가 없습니다.

그래서 단순 감에 의지하는 것이 아닌, **체계적인 지표** 를 가질 필요가 있습니다.

- **회귀 탐지 불가** — 프롬프트를 고치거나 모델을 바꾸거나 할 경우, 특정 답변은 좋아졌지만 기존 답변은 품질이 떨어지는 등의 경우를 알 수가 없습니다.
- **디버깅 지점 모호성** — RAG 파이프라인에서 오답이 나올 경우, '검색', '생성' 단계 등 어떤 지점에서 문제가 발생했는지 알 수가 없습니다.
- **비교 기준 부재** — 여러 모델 및 쿼리 등에 대해 객관적으로 비교할 수가 없습니다.
- **운영 도입 기준** — AI 의 가장 큰 문제는 불확실성인데, 정확도라는 지표가 없으면 서비스 출시 후 발생에 대응할 수가 없습니다.

#### & 소프트웨어 테스트 vs LLM 평가

| **구분** | 일반 소프트웨어 테스트 (Unit/Integration) | LLM 평가 (Evaluation) |
| --- | --- | --- |
| 입출력 | input output 이 명확 | 입력에 대한 아웃풋이 매번 다르다 |
| 성패 판단 | true/false 구분이 명확하다 | 의미, 유사도, 정확성 등 정도를 측정한다 |
| 검증 방식 | 코드 로직 검증 | 언어적 맥락 및 지식의 타당성 검증 |

#### & 회귀 검증(regression test) 개념과 Golden Dataset 의 연결

- 전통적인 개발에서 '회귀 테스트' 는 기존 기능이 깨지지 않았음을 보장하는데, LLM 에서는 **Golden Dataset** 을 필요로 합니다.
- 쉽게 말해 **모범 답안을 가진 질문/답안 세트로 구성된 데이터셋** 으로, RAG 파이프라인이 교체될 때마다 해당 질문 셋을 돌려서 확인하는 것입니다.

> 참고: <https://arxiv.org/abs/2306.05685>

#### & 자동 평가 vs 사람 평가 스펙트럼과 trade-off (비용·시간·신뢰성)

평가 방식은 크게 3가지로 나뉘며, **비용과 신뢰성 사이의 상충 관계** 를 가진다.

- **전통적 지표 (BLEU, ROUGE)**
  - 단어의 중첩도를 계산하며, 빠르고 저렴하지만 의미 유사도를 잡지는 못합니다.
- **인간 평가 (Human Eval)**
  - 가정 정확하지만, 느리고 비쌉니다.
- **LLM-as-a-Judge (자동 평가)**
  - LLM 에게 평가를 맡기는 것으로, 높은 정확도를 가지고 비용이 인간평가에 비해 저렴합니다.

> 참고: <https://arxiv.org/abs/2303.16634>

### 2-2. LLM-as-a-Judge

#### & 등장 배경

- **전통적 평가지표의 한계**
  - 기존 텍스트 생성 평가로는 BLEU 나 ROUGE 와 같은 참고 기반의 n-gram 자동 평가 지표들른 창의성과 다양성이 요구되는 작업에는 사람의 판단으로 한계가 존재
- **사람 평가의 비용적인 한계**
  - LLM 의 수많은 데이터를 사람이 평가하는 것은 비용과 시간이 너무 많이 들게 되어 LLM 을 평가자로 사용하는 방식이 등장했습니다.

#### & 작동 원리

- 평가지표를 LLM 에 제공하여, 이를 근거로 LLM 이 답변을 읽고 점수와 평가 근거를 출력하는 원리입니다.

#### & 사람 평가와 일치율

- LLM 은 사람과 높은 일치율을 보여줬습니다.
  - GPT-4 와 같은 모델을 평가자로 사용할 경우, 사람의 선호도와 **80% 이상 일치율** 이 나왔습니다.

#### & 루브릭 설계 원칙

- **명확성과 구체성**
  - 평가 기준과 원하는 출력 형태를 구체적으로 명시해야 합니다.
- **부정보다는 긍정적 지시 사용**
  - '하지 말아야 할 것' 보다는 '해야 할 것을 지시' 하는 게 좋다

> **나쁜 루브릭 예시** : 알 수 없는 내용이면 예측을 하지 마라
>
> **문제점**: '예측을 하지 않는다' 는 행동이 구체적으로 무엇인지 모호합니다.

> **좋은 루브릭 예시** : 알 수 없는 내용이 나오면, '질문에 대한 대답을 찾을 수 없습니다' 라고 대답해줘
>
> 평가 결과가 **이진법(Yes/No)** 으로 나뉠 만큼 명확합니다.

#### & 한계와 신뢰성

LLM 을 평가자로 두는 것도 결국 한계는 존재한다.

- **결과의 편향성**
  - LLM 은 답변이 제시된 순서에 영향을 받는 **위치 편향**, 길고 장황한 답변을 더 높게 평가하는 **장황함 편향**, 그리고 다른 모델보다 자기 자신(LLM)이 만든 텍스트에 높은 점수를 부여하는 **자기 고양 편향** 을 가질 수 있다.
- **추론의 한계**
  - 복잡한 문제에 있어서는 LLM 판정자 자체의 추론 능력의 한계가 평가 결과에 영향을 미칠 수 있다.

> 참고:
> - <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#leverage-thinking-and-interleaved-thinking-capabilities>
> - <https://arxiv.org/abs/2303.16634>

#### & Ragas 와의 관계

- **LLM Judge 기반 메트릭**
  - Ragas 의 4대 핵심 메트릭 중 생성된 답변이 문맥에 부합하는지 평가하는 **Faithfulness**, 질문과 답변의 연관성을 보는 **Answer Relevance**, 정답과 비교하는 **Answer Correctness**, 검색된 컨텍스트의 유용성을 평가하는 **Context Relevance/Precision** 등은 대부분 **LLM-as-a-Judge** 방식을 사용하여 프롬프팅을 통해 점수를 계산한다.
- **규칙 기반 메트릭**
  - 기존의 텍스트 일치율, 토큰 겹침을 보는 평가 방식, 특정 검색 지표 순위 수식 등의 계산 방식이 규칙 기반이다.

## 3. Ragas 4대 메트릭 (+ Answer Correctness)

### Context Precision (컨텍스트 정밀도) → 검색(Retriever) 단계

1. **정의**
   - Retriever(검색)가 query(질문)에 대해 청크들을 얼마나 잘 배치했는가에 대한 지표를 말합니다.
   - 관련 있는 정보들이 검색 결과의 얼마나 앞쪽에 몰려있는가를 나타내는 지표입니다.

2. **계산 방식**
   - 관련 문서가 상위 `k번째` 에 위치할수록 가중치를 두어 계산

3. **낮을 때 의심할 점**
   - 문서를 찾아냈으나, 중요한 정보가 하위 순위로 밀려나 있어 맥락을 놓치고 있을 가능성을 의심해봐야 한다.

4. **개선 기법**
   - Reranker 도입, 검색 쿼리 최적화를 고민해본다.

---

### Context Recall (컨텍스트 재현율) → 검색(Retriever) 단계

1. **정의**
   - 질문과 관련된 문서 중 얼마나 많은 양이 성공적으로 검색되었는지의 지표
   - 필요한 내용을 다 찾아왔는가의 여부이다.

2. **계산 방식**
   - (검색된 컨텍스트에 포함된 기준 정답의 주장 수) / (기준 정답의 전체 주장 수)
     - 기준 정답을 개별적인 claim 단위로 분리
     - 각 claim 이 검색된 컨텍스트에 포함되어 있는지 확인

3. **낮을 때 의심할 점**
   - 검색기가 답변의 핵심 단서가 되는 정보를 아예 검색 결과에 포함하지 못하는 것인지 찾아봐야 한다.

4. **개선 기법**
   - Top-k (검색 문서 갯수) 증가시키기
   - 청킹 전략 개선하기
   - 쿼리 전략 수립하기

---

### Faithfulness (충실도) → 생성(Generation) 단계

1. **정의**
   - 생성된 답변이 검색된 컨텍스트(근거)에만 기반하여 사실적으로 일치하는지 측정

2. **계산 방식**
   - (검색된 컨텍스트로 뒷받침되는 답변 내 주장 수) / (답변 내 전체 주장 수)

3. **낮을 때 의심할 점**
   - 환각이 발생하고 있는지 데이터 확인

4. **개선 기법**
   - 프롬프트 개선
   - 노이즈가 많은 문서 제거

---

### Answer Relevancy (답변 관련성) → 생성(Generation) 단계

1. **정의**
   - 생성된 답볍이 사용자의 질문의 의도에 맞게 답변되고 있는지의 지표
   - 사용자가 묻는 주제에 대해서만 답변을 하는지에 대한 지표

2. **계산 방식**
   - 질문과 답변을 각각 임베딩하여 역으로 생성된 질문들과의 코사인 유사도(Cosine Similarity) 평균

3. **낮을 때 의심할 점**
   - 엉뚱한 정보가 섞여있는지 확인

4. **개선 기법**
   - 프롬프트 지시사항 개선

---

### End-to-End 평가 — Answer Correctness

1. **정의**
   - 생성된 답변과 정답을 비교하여, 정확도를 측정하는 지표

2. **계산 방식**
   - 범위 0 ~ 1
     - 1 에 가까울수록 정답과 일치
   - (사실적 F1 Score) 와 (의미적 유사도) 를 결합한 가중치 평균

3. **평가 지표 2가지**
   - **사실적 유사도 (Factual Similarity)**
     - 답변과 정답을 statement 단위로 쪼갠 후, 공통된 정보를 비교
     - **TP (True Positive)**: 양쪽에 모두 있는 사실
     - **FP (False Positive)**: 답변에만 있는 잘못된 사실
     - **FN (False Negative)**: 정답에는 있는데 답변에 빠진 사실
     - → 해당 요소들로 F1 Score 를 계산합니다.
   - **의미적 유사도 (Semantic Similarity)**
     - 벡터 사이 거리 측정

4. **`ground_truth`(정답지) 품질 의존성**
   - 정답지가 얼마나 잘 구성되어 있는가에 따라 테스트 품질이 달라진다.

5. **Answer Correctness 만으로 부족한 이유**
   - Answer Correctness 가 낮다는 것이 답이 틀렸다는 결과만 알 수 있기에, 그 원인이 정확히 어느 지점인지 알 수가 없다.
   - 검색에서의 품질 저하인지, 생성에서의 품질 저하인지 원인 추적이 어렵다.

### 메트릭 간 관계

| **시나리오** | 낮아지는 메트릭 | 원인 | 대응 |
| --- | --- | --- | --- |
| 정답 청크 자체를 검색이 놓침 | Context Recall | 검색 엔진이 답변의 핵심 정보를 찾지 못함 | Top-k (검색 문서 갯수) 증가시키기<br>청킹 전략 개선하기 |
| 정답 청크는 있지만 8~10위로 밀림 | Context Precision | 하위권에 청크가 존재 | Reranker 도입, 검색 쿼리 최적화를 고민해본다 |
| 검색은 맞는데 LLM 이 외부 정보 추가 | Faithfulness | 환각 생성 | 프롬프트 개선 |
| LLM 이 질문을 잘못 이해 | Answer Relevancy | 질문 의도와 답변 내용 간의 불일치 | 프롬프트 개선 |
| 답은 맞는데 장황 | - | | |
